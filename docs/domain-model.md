# 领域模型

本文件定义概念，不提供方案。每条概念有唯一 owner、明确边界和一条不变量。
发现两处说法冲突，以本文件为准，并去 `decisions/` 记录修正。

## 从 harness 到组织的映射

整套方法论可以直接迁移，因为两者在结构上是同一个问题：
**一个能力固定的执行者，靠它周围的环境决定产出质量。**

| Harness（agent 的环境） | AI 原生组织（人 + agent 的环境） |
| --- | --- |
| 固定 worker（不换模型） | 固定编制与能力假设，不靠"再招个人"解决系统问题 |
| 上下文 | 信息流：谁必须知道什么、何时知道 |
| 工具 | 可调用的能力与数据 |
| 权限边界 | 决策权与授权包 |
| 非功能性需求 | 组织隐性约束：风险偏好、质量线、什么算做好 |
| 证明 | 验收契约与问责 |
| 反馈沉淀 | 复盘 → 规则 / 模板 / 检查 |
| 稀缺的上下文预算 | 稀缺的人类注意力 |

关键差别：软件里约束可以编译执行，组织里不能。所以组织设计必须为每条约束
补上一个**人工可判定的证据**，否则它只是口号。见 `proof.md`。

## 七个核心概念

### 1. 决策权 decision right
对某类后果性变更说"可以"的权力，含批准、否决、撤回。
**不是**：执行该变更的能力，也不是知情权。
**不变量**：每类后果性变更有且只有一个决策权 owner，且可指名到人。
owner: `authority.md`

### 2. 执行能力 capability
某个角色或 agent 实际能完成的操作集合。
**不是**：它"被允许"做什么。能力可以大于授权，也可以小于授权。
**不变量**：能力与授权分开登记，任何一方变化都不自动改写另一方。
owner: `authority.md`

### 3. 授权包 authority envelope
一次授权的完整契约：范围、时限、额度、审计方式、撤销人、回滚路径。
**不是**：一句"授予 XX 权限"。
**不变量**：没有回滚路径的授权包不成立。可逆环境里默认宽，后果性操作默认窄。
owner: `authority.md`

### 4. 证明契约 proof contract
"这个岗位 / 这次交付算完成"所需的证据，以及由谁判定。
**不是**：活动量、工时、token 数、产出的文档页数。
**不变量**：证据必须在真实环境可采集，且判定人不能是产出者自己。
owner: `proof.md`

### 5. 信息流 context flow
哪个角色在做哪类决策时，必须持有哪些当前事实，以及事实的权威来源。
**不是**：所有人都能看到所有信息（那是负载，不是上下文）。
**不变量**：每条关键事实只有一个权威来源；同一事实不允许多处手工维护。
owner: `context-flow.md`

### 6. 判断资产 judgment asset
一次决策沉淀下来的、能被下次复用的判断：一条规则、一个模板、一个检查、
或一个带适用边界的案例。
**不是**：会议纪要、聊天记录、原始轨迹。
**不变量**：必须带适用条件和失效条件，否则不允许进入资产库。
owner: `feedback.md`

### 7. 人类注意力 human attention
本项目的计量单位。所有方案最终比较的是：单位稀缺注意力换到多少
被接受的结果。
**不是**：人力成本，也不是自动化率。
**不变量**：任何提效主张必须写明省下的注意力去了哪里、换来了什么。
owner: `evals/README.md`

## 明确排除

本项目不研究模型能力评测、不研究提示词技巧、不产出组织架构图模板。
那些都是执行细节，不是决策结构。
