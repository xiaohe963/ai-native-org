# 证据等级与验收契约

这个领域最大的风险是产出听起来很对、但无法被否定的方案。
所以每条设计主张必须标等级，等级不够就不允许进入决策。

## 等级

| 级别 | 要求 | 能不能用来做决策 |
| --- | --- | --- |
| L0 | 一句主张，无案例、无边界 | 不能，只能当待验证假设 |
| L1 | 有至少一个真实案例，带时间、规模、来源 | 能启发，不能单独支撑决策 |
| L2 | 有可证伪条件 + 明确的适用边界 + 至少一条失败情形 | 可以，本仓库的默认门槛 |
| L3 | 在真实组织里跑过，或有对照，且记录了反面证据 | 可以作为规则推广 |

**规则**：`docs/` 下每条主张必须标注等级。低于 L2 的，文件名前缀加 `_draft-`。
`decisions/` 只允许引用 L2 及以上。

## 一份设计方案的验收

任何交付的设计方案，必须能回答这六问，答不出就是没完成：

1. 哪类后果性变更被识别了？决策权分别归谁（指名）？
2. 每个授权包的回滚路径是什么？谁执行回滚？
3. 每条约束在真实环境里由谁、用什么证据判定被满足？
4. 哪条关键事实只有一个来源？它现在在哪？
5. 这个方案在什么条件下应当被推翻？（必须写具体信号，不是"视情况"）
6. 省下的人类注意力去了哪里、换来了什么？

**禁止当作证据**：产出物数量、覆盖率百分比而无分母定义、agent 自述、
评审人的"感觉更清晰了"、只在演示环境跑通的流程。

## proof 与活动量的区别

测试通过只证明那条断言成立。同理，"复盘会开了"不等于"判断沉淀了"，
"文档写了"不等于"下次 agent 检索到了"。每个验收项都要指向一次
**可观察的行为变化**，而不是一次活动的发生。

## 与外部 harness 文集的对应

`harness-engineering/docs/proof/` 讨论的是构件身份与发布完整性；
本项目把它抽象成"组织里谁来判定、拿什么判定"。需要追溯原始论证时按需读，
不要复制进来。
