# 把反馈沉淀成资产

## 主张

> 一次事故、一次返工、一次"这次做得好"，只有在下一次同类决策变得更容易时，
> 才算被组织学到了。

**可证伪条件**：同类问题在三个月内重复出现，且没有人能从仓库里检索到
上次的结论，则上次的复盘没有产生资产。

## 沉淀到哪一层

按最早能拦住这个问题的位置放，越靠上越好：

| 观察到的缺口 | 最早的 owner | 沉淀形态 |
| --- | --- | --- |
| 概念被两种说法争用 | `docs/domain-model.md` | 定义 + 边界 |
| 权限与能力被混用 | `docs/authority.md` | 规则 + 授权包模板 |
| 交付说不清怎么算完成 | `docs/proof.md` | 验收项 |
| 现场缺一条权威事实 | `docs/context-flow.md` | 路由 / 投影 |
| 同类方案反复从零开始 | `playbooks/` | 流程步骤 |
| 一次具体取舍 | `decisions/` | ADR |
| 真实发生过的外部事实 | `cases/` | 案例卡片 |

## 什么不许沉淀

- 原始会话记录、长篇会议纪要、未整理的轨迹日志（留在 `runs/`）
- 没有适用条件的"金句"
- 只在一次运行中成立、且没有反面证据的因果归因
- 为让某条主张看起来成立而删掉的反例

##  gardening

每次跑完 job，检查：有没有新增一条可以从 `docs/` 里删掉的重复表述？
有没有一条 L2 主张被新案例削弱？删掉失去价值的控制，和加新规则同等重要。
