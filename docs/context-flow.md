# 信息流与上下文预算

## 主张

> 组织的信息问题通常不是"信息不够透明"，而是"决策时手边没有那条权威事实，
> 却同时被十条二手转述淹没"。

**可证伪条件**：若某类决策在信息完全开放的环境里仍反复因"不知道该信哪份"
而延迟，则问题在归属而非透明度——记录到 `cases/`。

## 设计规则

1. **大知识库，小工作集。** 事实留在权威系统里，决策现场只带当次需要的那几条。
2. 每条关键事实有且只有一个权威 owner。多处手工维护 = 没有 owner。
3. 区分三种信息：当前运行状态（会变，查系统）、稳定政策（版本化，查仓库）、
   判断先例（带边界，查 `decisions/`）。三者不要混放在一个"知识库"里。
4. 人肉转发是缺陷信号。每当有人把 A 系统的事实贴给 B 系统的人，
   记一次 `runs/` 里的 handoff 缺口，考虑把它变成可检索的投影。
5. 上下文预算按人类注意力算，不按字数算。加一份文档的代价是
   "以后每次相关决策都多读它"。

## 路由而非堆叠

`AGENTS.md` 是唯一的导航层。新增主题时优先问"该挂到哪条已有路由下"，
而不是新建一份总览。索引每多一份，就多一个会和它打架的索引。

## 反面清单

- 把整个外部语料复制进项目当"本地真相"（影子权威，会自己跟自己一致地漂移）
- 用"全员可见"代替"该知道的人在该时刻知道"
- 把一次会话的结论直接提升为长期政策
- 同一个版本号在政策文档、脚本、表格里各写一遍
