# ADR-012：判定规则可自定，但规则依赖的输入集合必须登记

```text
日期: 2026-11-12
状态: 提议
关联 run: runs/2026-11-12-JOB-0-run7.md；无 case（cases/ 为空）

决策:
1. 判定规则（怎么比对）可以写在契约命题里，不要求来自系统字段。
2. 判定规则依赖的输入集合必须登记。下列五类只要没有在 JOB-0 的登记表或
   decisions/ 的 ADR 中写明，就属于未登记约定：
   a) 路径 / 目录集合（文案路径、迁移脚本路径）；
   b) 清单（回归套件清单、服务清单、workflow 清单）；
   c) 命名规范（suite_name=迁移套件、migrations/**）；
   d) 自由文本的解析规则（impact_summary 如何拆成模块清单）；
   e) 字段语义（rollback_duration 是实测、估计还是 SLA）。
3. 依赖未登记输入集合的契约，只能标「假设可达」或「条件闭合」，
   不得计入「已登记可达」。
4. 判定句不得使用命题合取项之外的字段；用了，该条只能标「未闭合」。
   状态（元数据）与闭合（判定）分列，已登记不自动等于闭合。

当时的约束:
run7 首次盲测，JOB-0 只给了「依赖未登记的子字段、未填的账号表、或尚未
写入 ADR 的新约定」这一句原则，没有定义「约定」的边界。执行者把清单、
路径、命名归入「判定规则」，于是不算团队行为、不用登记：
- R7-P1 判定句用「PR 创建时间」，repo 补登表没有 created_at；
- R7-P4 判定句用「本迭代服务清单」，该清单未登记；
- R7-P5 判定句用「授权包约定的回滚时长上限」，是设计物；rollback_duration
  语义仍未定义（run6 的 G-R6-1）；
- R7-P7 把自由文本 impact_summary 当作可解析的模块清单；run6 的 P21 正因
  自由文本不可结构化而判未成立；
- R7-P9 用「迁移套件」这一未登记命名去匹配 suite_name；
- R7-P15 自己写「S 是本设计的回归清单（设计产物）」，却仍标已登记可达；
- R7-P16 用未登记的「文案路径集合」。
九条「已登记可达」中，只有 R7-P14、R7-P18 没有这类依赖。

考虑过的其他选项:
- 只改 JOB-0，不写 ADR：不采纳。ADR-010 的原则只住在验收标准里，run7 仍然
  找到了绕过方式；原则需要一条可引用的 ADR 才能被下一轮执行者当作规则。
- 把五类清单写进 2026-11-12 补登表：不采纳。补登表登记的是场景系统能力，
  清单 / 命名 / 解析规则是设计约定，写进去会把「场景事实」和「设计物」混在一起。
- 要求所有清单都必须进 JOB-0：不采纳。那会把任务契约膨胀成设计文档；
  本条只要求「依赖它的契约标假设」，不要求清单本身被批准。
- 给契约加第七列「输入集合」：不采纳。六字段已经够；输入集合写在命题的
  证据字段或假设说明里即可。
- 把「判定规则」也要求系统字段：不采纳。判定规则本来就是方案的一部分，
  不能要求系统提供；要管的是它的输入。

依据:
ADR-010：严格可达必须二分，依赖未登记约定的标假设。
ADR-008：闭合必须逐合取项覆盖，判定句不得超出命题。
ADR-003：证据能力门；未登记能力不得假定可达。
run7 §4.2 的七处证据（P1 / P4 / P5 / P7 / P9 / P15 / P16）；
run7 §4.3 P15 的「不声称」自己承认 S 是设计产物；
run7 运行记录「已登记 9 + 假设 2」与 §4.2 的实际依赖不一致。
以上依据是任务契约与运行文本的内部不一致，不是 cases/ 的 L2 主张；
因此本条标「提议」。

预期效果与验证方式:
下一轮盲测报告里：
1. 依赖清单 / 路径 / 命名 / 解析 / 语义的契约，不再出现在「已登记可达」；
2. 每条「已登记可达」能指出输入集合登记在 JOB-0 哪一行或哪条 ADR；
3. 判定句不再出现命题合取项之外的字段；
4. 报告仍写「已登记 X + 假设 Y」，且 X 会比 run7 的 9 小。
验证方式：抽查 3 条「已登记」契约，逐条问「这个清单 / 路径 / 命名 / 解析
规则在哪登记」；答不出，或只能答「这是判定规则」，该条本轮不成立。

推翻条件:
- 连续两轮执行者在没有 ADR-012 的情况下，仍能稳定标出五类依赖 →
  本条可降为一次性检查。
- 执行后已登记降到 0，且所有变更都不可授权 → 说明要求过严；应区分
  「高风险清单」（回归套件、权限范围）和「低风险约定」（普通文案路径），
  只对前者要求登记。
- 场景里其实已有这些清单（例如工单模板自带模块清单字段、发布平台自带
  服务清单）→ 对应条目可恢复为已登记可达，本条相应收窄。

已知局限:
- 只防五类输入集合，不防选错字段、字段名写错或选错命题。
- 不解决判定规则本身是否合理；规则可以登记齐全但仍然判错。
- 短期报告会更难看：假设条数上升，已登记下降。这是有意的，不是退步。
- 仍依赖执行者主动识别「我这条命题用了哪个输入集合」；若它把清单写成
  一句模糊的「相关模块」，本条拦不住，需要验收方逐条追问。
```
