# ADR-014：变更卡是后果性变更的单一登记载体

```text
日期: 2026-11-13
状态: 提议
关联 run: runs/2026-11-13-CHANGE-1.md；无 case（cases/ 为空）

决策:
1. 新增 templates/change-card.md，作为一次后果性变更的单一登记载体。
   一张卡必须同时包含：变更类别 / 影响面 / 可逆性、决策 owner、
   执行者 + 授权包六项、控制命题与业务命题分表、证据包封面（EPC）、
   proof 状态、残余风险接受。
2. 卡是登记面，不是证据本身；它不替代系统导出、EPC 归档、工单、PR、
   发布记录或数据快照。卡填得完整不等于变更安全。
3. 后果性变更没有卡，或卡缺少授权包六项、回滚路径证据来源、业务命题
   未闭合却无 owner 签署的残余风险接受，不得进入「已授权」。
4. 低风险、可逆、无外部影响、无审计要求的改动使用短表；不得用全卡
   制造仪式感，也不得用短表绕过后果性变更。
5. 残余风险接受只能由 owner 签署，只覆盖业务命题未闭合；它不能修补
   授权包缺项、回滚路径不可验证、证据缺失或判定人不独立。
6. 变更卡不重新定义概念。字段来源固定在模板 §14 的表中：变更判据与
   授权包归 docs/authority.md，证明契约归 docs/proof.md 与 JOB-0，
   严格可达/EPC/输入集合归 ADR-010 / ADR-011 / ADR-012。
7. 本仓库的变更类别 v1 登记为：D-1 导航契约修正（AGENTS.md、
   ARCHITECTURE.md 等导航与归属变更）；D-2 判断资产变更（模板、ADR、
   检查表等判断资产的新增或修改）。两类都走全卡；其他变更若不确定，
   按全卡填。该类别清单只在本仓库有效，不映射到 JOB-0 的 C-1–C-6。

当时的约束:
- 本仓库是文档项目，不是 JOB-0 的虚构产品公司；没有工单、CI、发布平台、
  权限系统。第一版变更卡用本仓库的一次真实变更（新增模板 + 接入导航）
  试填，不冒充 JOB-0 场景已发生。
- docs/ 不擅自改；ADR 仍为「提议」；cases/ 为空；无 L3。
- 本仓库没有版本控制，也没有登记级证据能力（git / 文件系统未在证据
  能力表中登记）；因此首张卡的证据只能到「假设可达」，闭合还取决于
  每个命题自己的字段与快照；回滚路径依赖变更前快照，不依赖系统审计。
- JOB-0 的六字段、五状态、合取项、业务命题分表已经稳定；本 ADR 只把
  它们组合成一张可执行的卡，不新增证明口径。

考虑过的其他选项:
- 把卡写进 docs/authority.md：不采纳。authority.md 的 owner 是规则与
  授权包定义，不是每次变更的登记面；写进去会让 docs/ 同时承担定义与
  运行记录，违反 ARCHITECTURE 的「论证与证据分开」。
- 继续用 JOB-0 的输出格式当卡：不采纳。JOB-0 是一次基准任务的完整报告，
  不是单次变更的授权载体；每类变更都要重新推导字段，且没有「待 owner
  批准 / 已授权 / 待验收」的状态。
- 只做系统字段表单：不采纳。文档、仓库、权限之外的变更有大量非系统
  证据；只做系统字段会逼执行者把非系统证据写成系统证据。
- 所有变更都套全卡：不采纳。低风险、可逆改动会被仪式拖慢，最后大家
  绕过卡；用 §13 短表分流。
- 让执行者代填残余风险：不采纳。违反 ADR-001（判定人必须是人）与
  ADR-007（业务命题未闭合不得授权）；代填会把「owner 接受」变成
  「agent 声明」。

依据:
docs/authority.md：规则 1（先列后果性变更）、规则 3（授权包六项缺一
  视为未授权）、规则 5（agent 不拥有批准权）。
docs/domain-model.md：证明契约的不变量——证据必须可采集，判定人不能是
  产出者自己。
docs/proof.md：六问、禁止当作证据的清单、L0–L3 等级。
ADR-006 / 008：证明契约先写命题，闭合逐合取项覆盖。
ADR-007 / 010：业务命题与可证命题分开；业务命题写到 owner 决策层；
  严格可达分已登记 / 假设。
ADR-011：EPC 是登记面，不是导出审计面；封面只证明采集人登记了什么。
ADR-012：判定规则可自定，但规则依赖的输入集合必须登记。
ADR-009 / 013：PR 评论留痕（release-go / copy-ok / postmortem /
  migration-review）作为非系统审批的载体。
runs/2026-11-13-JOB-0-run9.md：业务命题 0/6 闭合、C-2 / C-3 授权包
  未完成、EPC 只到登记层——这些缺口需要一个每次变更都能复用的登记面，
  而不是再写一份完整报告。
以上依据是任务契约与 ADR，不是 cases/ 的 L2 主张；cases/ 为空，
因此本条标「提议」。

预期效果与验证方式:
- 下一次后果性变更只填一张卡；owner 只读这张卡就能回答六问，不需要
  重读 JOB-0 或 run9。
- 验证方式（下一次真实变更时逐条检查）：
  1. 卡是否包含本 ADR 第 1 条列出的全部字段；
  2. 控制命题是否逐合取项有字段与判定句，且判定句不越出命题；
  3. 已登记 / 假设 / 待核 / 缺失 / 未成立是否分开计数，是否仍有合并比例；
  4. 业务命题是否写成 owner 的业务结果，而不是控制动作；
  5. 业务命题未闭合时，§11 是否有 owner 签署；空白时是否明确「不得授权」；
  6. 授权包缺项或回滚路径不可验证时，是否没有被残余风险接受掩盖。
- 可观察行为：变更评审时，owner 先看卡的总体结论与 §11；若卡没有
  「不得授权」或「已授权（带残余风险）」的明确结论，评审不开始。

推翻条件:
- 连续两次变更的卡在没有被 owner 阅读的情况下被批准，或 §11 被批量
  签署 → 卡退化为仪式，应减少字段或停用。
- 低风险变更因为全卡被明显拖慢，且短表仍无法分流 → 卡的门槛设计有误，
  应重划适用边界。
- 卡与 JOB-0 输出出现两套口径（同一命题两种状态、两种闭合定义）→
  先合并口径，再继续用卡。
- 组织没有证据能力登记，所有卡都只能到假设可达 → 先补登记，不要继续
  加字段；否则卡只是在把「未登记」写成「已分析」。
- 出现一次「卡显示已授权，但授权包缺项或回滚路径不可验证」的事故 →
  本条的门禁失效，必须重新审议，不得靠补一句说明过关。

已知局限:
- 无真实案例，L1 为空，无 L3；首张卡是本仓库的文档变更，不是产品发布。
- 卡是表单，不能替代判断；owner 仍可能把控制动作当业务结果，或把
  「字段齐全」读成「风险已覆盖」。
- 本仓库没有版本控制，也没有独立于执行者的第二方；首张卡的判定人
  只能是项目 owner，采集人可能同时是产出者，独立性只能靠「判定人
  独立重读」而不是系统审计。
- 短表与全卡的边界仍是判断；v1 只给了「可逆、无外部影响、无审计要求」
  三条，遇到边界情形需要 owner 裁定。
- 本 ADR 为「提议」；在它被接受前，卡里的 ADR 引用只能作为本卡约定，
  不能当作已接受的组织规则。
```
