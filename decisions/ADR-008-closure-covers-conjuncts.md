# ADR-008：证明闭合必须逐项覆盖命题，且先固化规则再补字段

```text
日期: 2026-11-12
状态: 提议
关联 run: runs/2026-11-12-JOB-0-run4.md

决策:
1. 「证明闭合」必须逐项覆盖命题的每个合取项。命题里有几个可独立判定的条件，
   就要有几组证据字段和判定句；缺任何一个合取项的字段、时点或判定句，
   只能标「未闭合」，不得标「闭合」。
2. 下一顺位先做 G-17（把「owner 表与契约表冲突时以契约表为准；每类变更
   单独登记业务命题」写进 JOB-0 验收标准），再做 G-14（补工单 4 个字段）。
   理由：G-17 是 run4 能发现 C-2 / C-5 / C-6 三处冲突的前提，现在只住在
   用户提示词里；不先固化，下一轮换执行者会重演宽命题的 owner 表。
   G-14 只关一条契约，可以后做。

当时的约束:
run4 的 9 条「闭合」里，P1 / P5 / P7 / P10 的判定理据只覆盖了命题的一部分：
- P1 命题含 approvals，闭合说明只写 artifact / commit / conclusion；
- P5 命题含「授权窗口内 + commit = 批准 PR head」，说明只写 workflow 成功；
- P7 命题含 release_go 已置位，说明只写 commit 匹配；
- P10 命题含 approvals，说明只写文件比对。
P2 和 P13 更严重：
- P2 命题要求 operator 是「发布前登记」的执行人，但工单没有 updated_at，
  E-2 记录也没有登记时间字段；只能证明「在名单内」，不能证明「发布前」。
- P13 命题说「线上文案」，证据链却是 commit + CI artifact + deployment artifact；
  这证明「部署制品来自已批准 commit」，不证明「线上页面实际渲染的文案」。
另外 P4 的「首个完整自然日」和「deployed_at 后 24h 内」不能同时成立：
23:30 发布，完整自然日结束于 24.5h 后；00:30 发布，完整自然日包含发布前 0.5h。

考虑过的其他选项:
- 只写 ADR，不改 JOB-0：不采纳。规则留在 decisions/ 且状态是「提议」，
  下一轮执行者可能不采纳；G-17 的缺口正是「规则只住在提示词里」。
- 先做 G-14，再做 G-17：不采纳。G-14 只让 R4-P16 闭合；G-17 决定下一轮
  还会不会重演「owner 表写宽命题、契约表写窄命题」的初稿。
- 把 P2 / P13 直接改写成窄命题并标闭合：不采纳。这是 ADR-007 禁止的
  「靠收窄命题消灭缺口」；应保留业务命题并标未闭合，或明确收窄后把
  收窄部分列为残余风险。
- 增加「部分闭合」状态：不采纳。四态 + 合取项检查已经够用；
  再加一态会变成分级表演。

依据:
ADR-006：证据字段必须能直接支持命题。
ADR-007：业务命题与可证命题分开；不得靠收窄命题消灭缺口。
run4 §4.2 的 P1 / P5 / P7 / P10 判定理据与命题的合取项不一致；
run4 §4.2 的 P2 / P13 证据链只支持更窄的命题；
run4 §4.2 的 P4 时点定义自相矛盾；
run4 运行记录 G-17：冲突裁决规则只在本轮用户指令里，未进验收标准。
（本条依据是 run4 文本的内部不一致与任务契约，不是 L2 设计主张；
  cases/ 为空，故标「提议」。）

预期效果与验证方式:
下一轮报告里：
1. 每条「闭合」契约的命题按合取项拆开，每个合取项都有字段和判定句；
2. P2 类命题要么收窄为「在名单内」，要么标「未闭合」并注明缺登记时间；
3. P13 类命题要么加 rendered_copy_hash / 页面快照，要么收窄为「制品层」；
4. P4 类时点只选自然日或滚动 24h 窗，不混用；
5. owner 表与契约表冲突时，owner 表不再声称契约表无法证明的命题。
验证方式：抽查 3 条「闭合」契约，逐项对照命题的合取项；若有一条缺判定句，
本轮闭合计数不成立。

推翻条件:
- 下一轮执行者在没有 G-17 规则的情况下，仍能稳定写出与契约表一致的 owner 表，
  且连续两轮无宽命题冲突 → G-17 可降为一次性检查。
- 若合取项检查导致契约数量爆炸、读者无法判断哪条是决策依据 →
  需要先冻结契约模板，而不是继续拆合取项。
- 若 P2 / P13 的字段在场景中其实存在（例如 E-2 记录自带可信时间戳、
  发布平台提供 rendered_copy_hash）→ 这两条可恢复为闭合，本条相应收窄。

已知局限:
- 本条只防「判定理据不完整」和「规则不落地」，不防「选错命题」或「字段名错误」。
- 合取项拆分会增加报告长度；对低风险、可逆变更可以简化。
- 本条仍依赖执行者主动拆合取项；若执行者把多个条件写成一句模糊命题，
  本条拦不住。需要在 JOB-0 验收标准里同时要求「命题必须可拆成可独立判定的条件」。
```
