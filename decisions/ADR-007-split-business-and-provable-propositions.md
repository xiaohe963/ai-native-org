# ADR-007：业务命题与可证命题必须分开登记，不得靠收窄命题消灭缺口

```text
日期: 2026-11-12
状态: 提议
关联 run: runs/2026-11-12-JOB-0-run4.md

决策:
当业务决策需要的命题宽于证据字段能直接支持的范围时，不得把命题改写成一句更窄、
刚好能被现有字段证明的话，然后宣称闭合。必须把它拆成两条：
  1. 可证命题：按 JOB-0 六字段登记，证据字段能直接支持，允许标「闭合」；
  2. 业务命题：单独登记，标「未成立」或「缺失」，写明缺哪个字段、哪个时点。
决策时只能引用可证命题。业务命题未闭合的变更不得授权，
除非场景 owner 明确接受残余风险并在运行记录中留痕。

当时的约束:
JOB-0 虚构场景；8 人团队 / 两周窗口 / 系统清单固定；
2026-11-12 四系统补登只覆盖工单、CI、发布平台、代码仓库；
2026-11-11 三个旧系统仍缺字段名、粒度、导出人；
cases/ 为空，无真实案例。

考虑过的其他选项:
- 只写可证命题：不采纳。方案会看起来全部闭合，业务风险被藏起来；
  读者无法知道「套件通过」不等于「兼容」。
- 只写业务命题：不采纳。无法判定真假，回到用措辞冒充证据的状态。
- 增设「部分闭合」状态：不采纳。四态 + 证明闭合列已经够用；
  再加一态会变成分级表演，而不是可执行的核对。
- 允许执行者自行把宽命题改写成窄命题：不采纳。这正是 run4 初稿 owner 表
  出现 C-2「迁移正确性」、C-5「兼容性」、C-6「设计稿一致」的原因；
  改写后看起来每条都有证据，实际上业务风险没有被判定。

依据:
ADR-006：证据字段必须能直接支持命题；缺命题或适用时点的不得标严格可达。
JOB-0.md「被接受的标准」：证明契约六字段缺一不可；严格可达只表示元数据齐全，
是否证明闭合必须另列一栏。
run4 的三个实例：
  - R4-P5 证明「迁移 CI workflow 成功」，不能证明「迁移数据正确」；
    R4-P6（行数 / 校验和）因此必须单独标缺失。
  - R4-P11 证明「已登记回归套件通过」，不能证明「套件外兼容」；
    R4-P12 因此必须单独标未成立。
  - R4-P13 证明「线上文案 = 已批准 commit 的文案」，不能证明「与设计稿逐字一致」；
    R4-P14 因此必须单独标缺失。
（注：上述依据是任务契约与 run4 的文本事实，不是带等级的 L2 设计主张；
  docs/ 主张仍未标等级（G-2），cases/ 为空。故本条只能标「提议」。）

预期效果与验证方式:
下一轮报告里，每条业务命题都能找到对应的可证命题，或者被明确标为缺失 / 未成立；
不出现「所有契约闭合」的单一结论。验证方式：
1. 检查是否存在一条业务上需要、但被改写成可证命题后消失的约束；
2. 检查每条「闭合」契约的命题是否真的覆盖了 owner 表声称的决策；
3. 若某类变更的业务命题未闭合，是否明确写了「不授权」或「残余风险留痕」。

推翻条件:
- 证据能力登记表覆盖了所有业务命题，且每条宽命题都有直接字段支持 →
  本条退化为一次性检查，可废弃。
- 执行者普遍能用一条命题同时满足业务与证据，无需拆分，且连续两轮没有出现
  「收窄命题后宣称闭合」的实例 → 本条可降为可选项。
- 拆分导致契约数量爆炸（每条变更拆成十几条），且读者无法从清单判断哪条是
  决策依据 → 需要先冻结一套契约模板，而不是继续拆分。

已知局限:
- 本条只防止「收窄命题」这一种规避；它不能防止「选错命题」或「字段名错误」。
- 它可能增加契约数量；对低风险、可逆、无审计要求的变更可以简化，不必套用。
- 它依赖执行者主动区分业务命题与可证命题；若执行者不写业务命题，
  本条仍然拦不住「只写可证命题」的做法。需要 JOB-0 验收标准同时要求
  「每类变更的业务命题是什么」。
```
