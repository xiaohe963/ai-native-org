# ADR-003：证明契约先过证据能力门，不过门的条目写「未成立」而不是换说法

```text
日期: 2026-11-11
状态: 提议
关联 run: runs/2026-11-11-JOB-0-run2.md

决策:
写证明契约前，先对每条证据做可达性核对，结果三态标注：
已登记可达 / 系统存在但能力未登记（未成立）/ 清单内无来源（缺失）。
系统「存在」不等于「可作证据」。未登记能力的系统，其输出不得用于判定交付完成，
只能用于提示风险。
当一条验收条目找不到可达来源时，允许的处置只有两种：换成表内可达的证据源，
或明确标「未成立」。不允许第三种处置——用措辞让它看起来成立。

当时的约束:
JOB-0 证据能力清单只登记 3 个系统（客户反馈渠道日粒度、线上问题等级、
权限系统审计日志），而本链路核心证据（代码 diff、CI 结果、部署记录）
所在系统未登记。两周时间窗内无法补建任何新系统。

考虑过的其他选项:
- 假设 CI / 发布平台「显然」能提供证据：不采纳。这正是 JOB-0 正文禁止的
  自行假设；且「显然能」与「已登记可导出」之间差的是一整套权限与字段定义。
- 把所有依赖未登记系统的条目删掉，只交 3 条：不采纳。会掩盖缺口，
  让下一个执行者以为这条链路的证明面本来就只有 3 条。
- 用人工观察替代系统证据并标为达成：不采纳。人工观察的判定人往往就是产出人，
  违反证明契约不变量，且会产出「已核对」的假信号——比没有判定人更危险。

依据:
JOB-0.md「外部系统证据能力清单」正文：未列出的能力视为不可达；不得把未列出的
  能力假定为可达；需要某条证据时要么换成表内可达的证据源，要么把该条明确标为
  「未成立」，不得静默带过。
docs/proof.md：禁止当作证据的清单包含 agent 自述；每个验收项要指向可观察的
  行为变化，而不是一次活动的发生。
（注：上述 JOB-0 条文是任务契约，不是带等级的设计主张；docs/proof.md 的主张未标
  等级，该缺口记为 G-2。依据不足 L2，故本条标「提议」。）

预期效果与验证方式:
JOB-0 交付物的证明契约 13 条里，4 条标可达（其中 1 条仅部分成立）、7 条标未成立、
2 条标缺失；缺口以「4/13」这一可复核的比例呈现，而不是以「基本覆盖」这类措辞呈现。
验证方式：换一个执行者重跑同一 job，看其给出的可达比例与本条是否同量级；
若新执行者给出显著更高的可达率，核查其是否把未登记系统当成了可达。

推翻条件:
出现一类交付，其验收条目的证据只能由人工观察获得，且判定人可被证明独立于产出人
（例如由客户直接确认）。此时「人工观察不构成证据」这条需要放宽，
本决策的三态标注退化为两态。
或：证据能力清单被补登到覆盖链路主体后，「未成立」成为罕见状态，
本条从常规动作退化为一次性前置检查。

已知局限:
本条只能防止「静默带过」，不能创造证据。4/13 这个比例说明的是登记不全，
不是方案本身的证明强度——两者容易被混读，需要在交付物里分开陈述。
cases/ 为空，无 L3 证据。
```

## 与 ADR-001 的关系

ADR-001 处理的是「判定人是谁」（agent 产出时必须由人判定）。本条处理的是「判定所依据的东西存不存在」。两者是串联关系，不是替代：判定人再独立，若他手里的证据来自一个未登记能力的系统，那条验收仍然是空的。

顺序上应先满足本条，再满足 ADR-001——没有证据时，讨论判定人的独立性没有意义。
