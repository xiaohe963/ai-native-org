# ADR-004：证据能力补登是场景契约修订，不是能力改善证据

```text
日期: 2026-11-12
状态: 已接受（效力仅限 JOB-0 场景契约）
关联 run: runs/2026-11-11-JOB-0-run2.md

决策:
为工单、CI、发布平台、代码仓库各补登三个字段（谁能导出 / 粒度 / 字段名），
写入 JOB-0.md「外部系统证据能力清单」。补登后，此前 7 条「未成立」与 1 条
「部分可达」的 CI 部分应由不可达转为可达；数据迁移校验与线上文案比对
仍为「缺失」。
补登值按场景的常见系统形态起草，作为场景契约生效；它们不是对任何现实组织
的现场观察。

当时的约束:
JOB-0 是虚构场景；60 人公司 / 8 人团队 / 无专职 DBA 与安全岗 / 两周时间窗。
场景只列系统清单，未列证据能力。run2 因此把 7 条证明契约标为「未成立」、
2 条标为「缺失」，可用条目 4/13。

考虑过的其他选项:
- 保持现状，等真实组织提供能力清单：不采纳。JOB-0 是基准任务，没有补登
  就无法进入下一轮对照；但不能把补登当成现实事实。
- 让执行者按「常见系统应该能导出」自行假设：不采纳。这正是 run1 的失败模式，
  JOB-0 正文明确禁止静默假设。
- 只补登「系统存在」，不写字段名：不采纳。字段名是证明契约可执行的最小单位；
  没有字段名，「可达」仍是一句口号。

依据:
JOB-0.md「外部系统证据能力清单」登记规则：未列出的能力视为不可达；需要某条
证据时，要么换成表内可达的证据源，要么明确标「未成立」。
runs/2026-11-11-JOB-0-run2.md G-3：补登四个系统各三个字段是最小干预。
用户 2026-11-12 指令：执行 G-3。
（注：本条依据是场景 owner 的授权与 JOB-0 的登记规则，不是 L2 设计主张。
它记录一次契约修订，不进 L2 阶梯，也不得被引用为设计结论。）

预期效果与验证方式:
下一轮全新会话重跑 JOB-0，证明契约可用条目应为 11/13；数据迁移校验与
线上文案比对仍为缺失。验证方式：
1. 新运行是否为每条「可达」证据写明具体字段与判定人，而不是只写系统名；
2. 新运行是否仍把两条缺失项标为缺失，没有用「人工核对」冒充系统证据；
3. 新运行是否把 11/13 当成「方案变好」的证据——若是，判本次补登被误用。

推翻条件:
- 真实组织核对后发现四个系统中任一系统的字段 / 导出人与本表不符，且该差异
  影响判定 → 该行退回「未成立」，本 ADR 需要一条替代记录。
- 下一轮重跑中，执行者把补登表当作「现实已具备」的事实引用，而没有引用
  场景契约声明 → 说明 provenance 没起作用，应把声明提到表头更显眼的位置，
  或改回「待确认」三态。

已知局限:
- 补登值是场景契约的起草值，不是现场核验值；它只保证 JOB-0 可重跑，
  不保证任何真实公司具备这些能力。
- 11/13 是「给定能力下的上限」，不是方案有效性的度量；4/13 → 11/13 的差异
  来自场景变更，不来自设计改进。
- 既有 3 个系统（客户反馈渠道、线上问题等级、权限系统）仍未补登导出人与
  字段名；本 ADR 不覆盖它们，避免一次改太多。
```

## 为什么不标「提议」

ADR-001 / 002 / 003 标「提议」，是因为它们依据的是设计主张，而 `docs/` 的
主张未标等级（G-2）、`cases/` 为空。本条不是设计主张：它记录的是一次由
场景 owner 授权的契约修订，效力仅限 JOB-0 的虚构场景，且不引用任何 L2 结论。

若把它标成「提议」，会让人误以为补登尚未生效；若把它当成设计结论，又会
违反 provenance。两种误读都写进了上面的推翻条件。
