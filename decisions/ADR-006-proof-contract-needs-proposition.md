# ADR-006：证明契约必须先写命题，再写证据

```text
日期: 2026-11-12
状态: 提议
关联 run: runs/2026-11-12-JOB-0-run3.md

决策:
证明契约的每条必须包含六个字段：命题（要证明的约束）、适用时点 / 范围、
证据字段、采集人（导出人）、判定人、状态。缺命题或适用时点的，不得标
「严格可达」，只能标「待核」。
ADR-005 的四条件（系统在清单内、字段已登记、导出人可指名、导出带时间戳 /
操作者）保留为「元数据可达」；另设「证明闭合」：证据字段必须能直接支持
命题，且命题的适用时点 / 范围明确。报告时两列分开，不得合并成一个比例。
本条对应的缺口记为 G-13（证明契约缺命题与适用时点）。

当时的约束:
run3 的 13 条契约只有 ID / 覆盖类别 / 证据字段 / 采集人 / 判定人 / 状态，
没有命题列。§2 的 owner 表用 P-ID 指代具体证据，但 §4.2 的证据字段
与 §2 的命题不一致：
- C-2 说 P-5 证明「回滚可行性与不可逆点」，P-5 的证据是 impact_flags /
  impact_summary / request_reason / use_case + changed_files / diff_stat，
  没有回滚段、不可逆点或书面确认；
- C-4 说 P-9 证明「兼容性结论」，P-9 的证据是 dependency_files / diff +
  CI suite_name / conclusion；CI 绿是测试通过，不是兼容性结论；
- C-6 说 P-4 是「发布后健康证据」，P-4 的证据是 deployment_id / status /
  operator / deployed_at / revision；这是部署记录，不是健康证据，
  健康证据是 P-3。
因此 8/13「严格可达」是元数据口径：系统、字段、导出人、时间戳齐全，
不等于证据能证明该条约束。

考虑过的其他选项:
- 先做 G-10（补登三个旧系统），把 8/13 变成 11/13：不采纳为第一顺位。
  会得到 11 条「字段齐全」，但 P-5 / P-9 / P-4 的命题仍不闭合；
  这会把元数据齐全误读为证明闭合，正是 ADR-003 / ADR-005 要防的事。
- 只修 §2 的措辞，把 P-5 / P-9 / P-4 改写成它们实际能证明的命题：
  部分采纳。若命题只是措辞问题，改 §2 即可；但 §4.2 仍缺命题列，
  下一轮换执行者还会出现同样的错配，所以需要 schema 级约束。
- 把 8/13 全部降为「待核」：不采纳。它们的元数据确实齐全，
  降为待核会丢掉「哪几条缺字段」这一可复核事实；应新增「证明闭合」
  维度，而不是改写元数据状态。
- 重写 run3 的交付物：不采纳。运行记录是历史事实，不能改；
  本条只约束下一轮。

依据:
docs/proof.md 六问第 3 问：每条约束由谁、用什么证据判定被满足？
run3 §8 第 3 问答的是「13 条契约逐条写证据字段、采集系统、导出人、判定人」，
没有回答「每条约束是什么」。
JOB-0 交付物 4：每类交付的证明契约——什么证据、从哪采、谁判。
「什么证据」必须绑定一个命题，否则无法判断证据是否充分。
ADR-005：四态解决「可达」的元数据条件，但不解决「证据是否支持命题」。
（注：本条依据是 run3 的内部不一致与 docs/proof.md 的六问，不是 L2 设计
  主张；cases/ 为空，故标「提议」。）

预期效果与验证方式:
下一轮重跑的报告里，每条契约先写命题，再写证据；P-4 / P-5 / P-9 要么
补上能支持命题的字段，要么改标「未成立」或「待核」。验证方式：
1. 是否每条契约都有「命题 + 适用时点 / 范围」两列；
2. 是否出现「证据字段与命题不匹配」的条目被如实标为未成立，而不是
   靠改措辞过关；
3. 严格可达的数量可能低于 8/13；若低于，是否给出了具体的字段缺口，
   而不是笼统地说「证据不足」。

推翻条件:
- 若下一轮执行者在不加命题列的情况下，仍能为每条契约写出与其 §2
  用途一致的证据，且无错配 → 说明本次错配是 run3 的执行问题，
  不是 schema 问题，本条可降为一次性检查。
- 若命题列导致契约数量爆炸（每条变更拆成十几条），说明需要先冻结
  一套契约模板，而不是继续加字段。

已知局限:
- 本条只改契约的写法，不创造证据；它可能让严格可达的数量下降，
  这是纠正高估，不是退步。
- 低风险、可逆、无审计要求的变更可以简化，不必套六字段；
  本条针对后果性变更。
- run3 是单次运行；本条的依据是 run3 文本的内部不一致，不是
  多轮对照；它需要下一轮验证。
```

## 为什么这会改变下一顺位

run3 建议的第一顺位是 G-10：补登 2026-11-11 三个旧系统的导出人 / 粒度 /
字段名，把严格可达从 8/13 推到 11/13。这个干预本身没错，但它改善的是
**元数据完整度**；在契约没有命题列的情况下，它无法区分下面两件事：

- 11 条契约的字段、导出人、判定人都齐了；
- 11 条契约的证据真的能证明各自要证明的约束。

P-5 / P-9 / P-4 已经证明这两件事不是一回事。先做 G-10，下一轮很可能
得到「11/13 严格可达」的新数字，但错配仍然存在，只是被更完整的元数据
盖住了。因此本条把第一顺位改为：先补契约 schema（命题 + 适用时点），
再做 G-10。

## 其他观察，不在本条决策范围

1. **待核理由不一致**：P-3 / P-7 / P-8 的契约表已写出导出人（QA、系统
   管理员），但状态说明仍写「导出人未登记」。按 ADR-005 字面（导出人可
   指名），条件③已满足，缺的是字段名 / 粒度；按「登记表确认」口径，
   ③未满足，但应写「角色推断，未登记确认」。两种口径不能在同一个
   「待核」标签下混用，否则下一轮不知道该补字段还是补导出人确认。
2. **P-ID 跨运行复用**：run2 与 run3 的 P-1 至 P-13 含义不同；run3 未读
   run2 交付物正文，所以不会察觉。G-9 只处理了分母，没有处理 ID 语义。
   建议 P-ID 带运行前缀（如 R3-P1），或冻结一套契约 ID；这也是平台存
   证明契约时的数据模型要求。
3. **运行记录的措辞偏差**：run3 记录写「3 条待核明确写『字段 / 导出人
   未登记』」，但 §4.2 的表格写了导出人。建议在记录末尾追加一条更正，
   不要改原文。
4. **外部参考路径未固化**：早期 README / AGENTS 指向一个本机绝对路径，
   而不是仓库内可移植的相对路径。run3 未触发外部参考条件，所以没有暴露；
   下一位执行者一旦需要外部论点就会断。
