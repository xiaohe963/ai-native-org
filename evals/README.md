# 评估这套 harness 有没有用

要测的不是"agent 有没有提到这些术语"，而是**同一个执行者在有/无这套上下文时，
产出的设计方案是否更可被接受**。

## 先定决策

每次评估只回答一个问题，例如：
「`docs/authority.md` 是否让 agent 更少把能力和授权混为一谈？」

写下来再跑，否则会退化成挑好话。

## 条件设置

- 固定执行者与配置、同一场景、同一预算、同一权限边界、同一交付清单。
- 唯一差异：是否提供本仓库的 `AGENTS.md` 与按需路由。
- 全新会话，随机顺序，每个条件重复多次，保留所有失败运行。
- 换模型或换 agent 时，重新开一个评估周期，不和历史数据混比。

## 四个维度分开打分

| 维度 | 看什么 | 是否决定接受 |
| --- | --- | --- |
| 结果 | 六问能否逐条可答、授权包是否齐全 | 是 |
| 证明 | 证据是否真实可采集、判定人是否独立 | 是 |
| 结构 | 是否没有制造重复定义、是否守住 owner | 是 |
| 轨迹 | 耗时、重试、人肉补传次数 | 否，只用于解释成本 |

具体实现细节、措辞、文件顺序不算要求，除非契约里写明。

## 必须记录的四件事

干预是否**可用 / 被检索 / 被调用 / 与本次决策相关**。
一次运行从没打开过 `authority.md`，就不能拿它的成功来说明那份文档有效。

## 什么结果无效

- 单次 rollout 当成普遍结论
- 把 agent 的自评当成 proof
- 拿 token 数、文档数、覆盖率当结果
- 评估方另建一套"标准答案"语料，自己跟自己对答案
- 两个条件的写权限或可执行检查不对等

## 长期问题

真正要测的是：后来的一次设计，是否用上了前一次沉淀的判断。
跑完 JOB-0 之后，隔一段时间用同类但不同规模的场景再跑一次，
看复发率、人肉补传次数、proof 质量有没有变化。
一次前后对比不能证明因果，只能说明"这次跑通了"。
