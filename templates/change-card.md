# 变更卡（Change Card）v1.1

> 一张卡承载一次后果性变更的「授权 + 验收」。owner 只读这一张卡，就应当能
> 回答：批不批、依据是什么、哪些证据已登记、哪些只是假设、业务结果有没有
> 闭合、接受了哪些残余风险。
>
> 本卡是登记面，不是证据本身。它不替代系统导出、证据包封面（EPC）归档、
> 工单、PR、发布记录或数据快照。

## 0. 适用边界

**适用**：后果性变更——不可轻易回滚 / 影响外部用户 / 涉及资金、数据、权限、
发布（`docs/authority.md` 规则 1）。一次变更跨多个类别时，只设一个主类别、
一个 owner；其余类别的决定作为证据产出，不进入授权表。

**不适用**：可逆、无外部影响、无审计要求的低风险改动。不要为了凑数填全卡；
用 §13 的短表。若不确定，先问「错了能不能轻易回滚」。

**门禁**（缺一不得进入「已授权」）：

1. 变更类别已登记，且写明为什么是后果性；
2. 决策 owner 指名到具体人，不是角色占位；
3. 每个执行者的授权包六项齐全；
4. 回滚路径有可验证的证据来源，不是「应该有」；
5. 每条控制命题六字段齐全，合取项逐项有字段和判定句；
6. 依赖的输入集合已登记，未登记的单列假设；
7. 业务命题未闭合时，owner 已在 §11 签署残余风险接受；
8. 使用 git 作为回滚 / 证据来源时，变更前已记录 `base_commit`，且变更前
   `git status --porcelain` 为空。前置检查必须在编辑前完成，事后补记无效。

第 7 条不能修补第 3、4、8 条的缺失。授权包缺项、回滚路径不可验证或 git
前置检查未完成，只能补，不能靠接受残余风险过关。

## 2. 变更类别与纳入理由

| 项 | 内容 |
| --- | --- |
| 类别 | 引用组织的后果性变更清单。示例：C-1 常规发布 / C-2 数据迁移 / C-3 权限调整 / C-4 外部依赖升级 / C-5 客户可见文案 / C-6 紧急修复；本仓库自有类别为 D-1 导航契约修正、D-2 判断资产变更，类别清单登记在 ADR-014 决策 7。组织用自己的清单，不要把示例当成本组织的已登记类别 |
| 为什么是后果性 | 逐条回答：错了能否轻易回滚？影响外部用户吗？涉及资金、数据、权限、发布吗？ |
| 跨类别处理 | 主类别 / 合并理由 / 唯一 owner；其余类别只作为证据产出 |
| 不纳入的相邻变更 | 写明本次不改什么；相邻变更另开卡，不顺手扩大范围 |

## 3. 影响面

| 项 | 内容 |
| --- | --- |
| 受影响对象 | 外部用户 / 内部角色 / 系统 / 数据 / 权限 / 外部依赖 / 客户可见文案 |
| 爆炸半径 | 单服务 / 多服务 / 全站；数据范围（表 / 行数 / 租户）；文件范围 |
| 检测延迟 | 即时 / 小时 / 天；靠什么发现 |
| 不可逆点 | 具体动作或时刻（迁移执行、权限生效、文案触达、外部通知） |
| 关键事实与权威来源 | 每条事实一个来源；标出人肉转发点（`docs/context-flow.md`） |
| 明确不声称的影响面 | 本卡不覆盖什么 |

## 4. 可逆性

| 项 | 内容 |
| --- | --- |
| 可逆等级 | 可轻易回滚 / 可回滚但有用户影响 / 部分不可逆 / 不可逆 |
| 回滚动作 | 具体操作，不是「回滚即可」 |
| 回滚执行人 / 复核人 | 执行人不得是唯一复核人 |
| 回滚路径的证据来源 | 系统.字段 + 登记位置；例如 `previous_revision` + 历史 deployment 记录 |
| 变更前基线（有版本控制） | 编辑前记录 `base_commit`（完整 SHA），且 `git status --porcelain` 为空；事后补记无效。字段口径见 ADR-015 |
| 变更前快照（无版本控制） | 变更前文件副本 + SHA-256 + 存放位置；缺快照视为回滚路径不可验证 |
| 回滚验证命题 | 指向 §7 的控制命题 ID |
| 回滚后的状态 | 数据一致性 / 权限恢复 / 文案撤回，各自单独命题 |
| 时长语义 | 使用 RTO / `rollback_duration` 时，写明是实测、估计还是 SLA；未登记语义不得作判定句 |
| 不可逆点处置 | 快照 / 备份 / 双人复核 / 不接受；写明选哪个 |

**门**：回滚路径没有证据来源，或「可回滚」只有布尔值没有历史记录，
本卡不得进入「已授权」。这不是残余风险能补的项。

## 5. 决策权 owner

| 项 | 内容 |
| --- | --- |
| owner | 角色 + 姓名 / 账号（必须是具体人；角色占位不算） |
| 为什么是这个角色 | 问责理由，不是「他一直做这个」 |
| 明确不授予 | agent / 执行者不得做什么 |
| 第二方 | 证据产出方，不是共同 owner；产出什么证据；持有「拒绝产出证据」的权力（ADR-002） |
| 跨类别冲突 | 每类只有一个 owner；跨类别只保留一个；写合并理由 |
| owner 缺席 | 代理人是谁；代理是否改变问责；不得写「共同负责」 |

## 6. 执行者与授权包

### 6.1 执行者登记

| 执行者 | 人 / agent | 具体动作 | 明确不做 |
| --- | --- | --- | --- |
|  |  |  |  |

### 6.2 授权包（每个执行者一份，六项）

```text
执行者:
变更类别:
授权范围:
有效期 / 触发失效条件:
额度或频次上限:
审计记录位置:
撤销人:
回滚路径与验证方式:
决策权 owner（指名到人）:
执行者（人 / agent）:
```

六项 = 范围 / 时限 / 额度 / 审计 / 撤销人 / 回滚路径。owner 与执行者是
身份字段，不计入六项；缺任一项仍视为未授权（`docs/authority.md` 规则 3）。

### 6.3 授权包完整性核对

| 变更类别 | 涉及授权包 | 六项是否齐全 | 回滚路径是否可验证 | 结论 |
| --- | --- | --- | --- | --- |
|  |  |  |  | 完整 / 未完成 |

判定独立性：

- 判定人不得是该条变更的产出者（`docs/domain-model.md` 证明契约不变量）；
- agent 产出的交付，判定人必须是人（ADR-001）；
- 采集角色 ≠ 产出角色，只能证明角色隔离；不得宣称系统审计（ADR-011）。

## 7. 控制命题

### 7.1 控制命题表

| ID | 命题（合取项逐项编号） | 适用时点 / 范围 | 证据字段（系统.字段 + 子字段登记位置） | 采集人（角色 + 账号） | 判定人（不得是产出者） | 状态 | 闭合 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| P1 | (1) …；(2) … |  |  |  |  |  |  |

状态五值：已登记可达 / 假设可达 / 待核 / 缺失 / 未成立（ADR-005 / ADR-010）。
闭合三值：闭合 / 条件闭合 / 未闭合（ADR-008）。
「已登记可达」只表示元数据齐全；是否闭合另列一栏，不得合并成一个比例。

### 7.2 合取项拆分

| 契约 ID | 合取项 | 证据字段 | 判定句 |
| --- | --- | --- | --- |
|  |  |  |  |

每个可独立判定的合取项都要有字段、时点和判定句；缺一个，整条只能标
「未闭合」（ADR-008）。判定句不得使用命题合取项之外的字段；用了，
该条只能标「未闭合」（ADR-012）。

### 7.3 假设清单

| 假设 ID | 内容 | 类别 | 影响的契约 | 若不成立 |
| --- | --- | --- | --- | --- |
| A-1 |  | 对象子字段 / 账号表 / ADR-012 五类 / 其他 |  |  |

假设不得并入「已登记可达」；报告写「已登记 X 条 + 假设 Y 条」，不得只写
一个总数（ADR-010）。

### 7.4 输入集合登记

| 契约 ID | 输入集合 | 类型（路径 / 清单 / 命名 / 解析 / 语义） | 登记位置 | 是否已登记 |
| --- | --- | --- | --- | --- |
|  |  |  | JOB-0 行号 / ADR 编号 / 未登记 |  |

判定规则可以自定；判定规则依赖的输入集合必须登记。未登记的，契约只能标
「假设可达」或「条件闭合」（ADR-012）。

### 7.5 对象型 / 列表型字段核查

| 字段 | 类型 | 被哪些契约使用 | 子字段 / 元素属性 | 是否逐项登记 | 结论 |
| --- | --- | --- | --- | --- | --- |
|  | 对象 / 列表 / 标量 |  |  |  |  |

对象型字段的子字段默认未登记，除非登记表逐项列出；只写对象名不等于登记
了子字段。列表型字段的元素不视为子字段；若元素本身是对象，其属性默认
未登记（JOB-0）。

### 7.6 时点与环境层

- 涉及线上 / 生产环境的命题，必须写明证据是**制品层**还是**渲染层**；
  两层不能互相代替。
- 涉及「24 小时 / 首日」的命题，必须二选一：自然日或滚动 24 小时窗；
  不得同时写「首个完整自然日」和「24 小时内」。
- 涉及「发布前 / 发布后」的命题，必须写明时间基准（`deployed_at` /
  `created_at` / 执行开始时间）。

### 7.7 不声称

每条契约都要写一句「本证据不证明什么」。没有「不声称」的契约，视为
把证据的边界留给读者猜测。

## 8. 业务命题（与控制命题分表）

| ID | 变更类别 | 业务命题（owner 要决定的业务结果） | 映射控制命题 | 逐合取项状态 | 业务状态 |
| --- | --- | --- | --- | --- | --- |
| B-1 |  |  |  |  | 闭合 / 未闭合 |

业务命题必须写成 owner 要决定的业务结果，不能写成控制动作（如「行数一致」
「24h 补单」）。每条业务命题至少映射一个控制命题；控制命题闭合不等于
业务命题闭合。业务命题未闭合时不得授权，除非按 §11 签署残余风险
（ADR-007 / ADR-010）。

## 9. 证据包封面（EPC）

### 9.1 主封面

```text
EPC ID: <契约ID>-<发布单/工单/变更单ID>-<序号>
契约 ID:
证据系统:
导出账号:
导出时间: ISO 8601，含时区（+08:00）
导出对象 ID: ticket_id / workflow_run_id / deployment_id / pr_number / 文件路径
导出文件 SHA-256:
采集人（角色 + 账号）:
判定人（角色 + 账号）:
核对时间:
核对结论: 字段齐全 / 缺字段（列明）/ 对象 ID 不匹配 / 账号不属于采集角色
备注:
```

### 9.2 多系统导出记录

| 系统 | 导出账号 | 导出时间 | 导出对象 ID | 文件 SHA-256 | 备注 |
| --- | --- | --- | --- | --- | --- |
|  |  |  |  |  |  |

一个多系统契约用「一张主封面 + 每个系统一行导出记录」；不得把一个账号 /
时间覆盖三个系统，也不得把三个对象 ID 塞进一行。

### 9.3 封面边界

封面只证明「采集人登记了哪个账号、哪个时间、导出了哪个对象」，不证明
「系统确认该账号执行了导出」。判定人只能核对四项：

(a) 导出账号属于采集人角色；
(b) 导出时间落在适用时点窗内；
(c) 导出对象 ID 与契约范围一致；
(d) 文件 SHA-256 与归档件一致。

系统未登记 `export_actor` / `exported_at` 时，独立性只能按
「采集角色 ≠ 产出角色」判定，不得宣称系统审计（ADR-011）。

### 9.4 仓库 / 文档类变更的 EPC 变体

```text
证据系统: 代码仓库 / 文件系统
导出账号: 本地工作区账号（若系统不提供导出审计，写明「不可由系统审计」）
导出时间: 快照 / 读取时间
导出对象 ID: 文件路径 + 变更前 SHA-256 / commit_sha（若可用）
导出文件 SHA-256: 变更前与变更后各一份
变更前基线: base_commit = <完整 SHA>；变更前 git status --porcelain 为空
变更提交: change_commit = <完整 SHA>；变更后 git status --porcelain 为空
采集人: 执行快照的人；若与产出者同一人，判定独立性只能由判定人独立重读
判定人: 人；不得是执行者
核对结论: 登记层 / 不可判定
```

仓库没有版本控制时，回滚路径必须包含变更前快照（副本 + SHA-256）；
没有快照的回滚路径只能标「不可验证」。

本仓库的 git 字段、粒度、导出人与边界登记在
`decisions/ADR-015-git-repository-evidence-capability.md`；使用前先核对
该 ADR 的状态（当前：已接受）与第 5 条使用条件。

## 11. 残余风险接受（owner 签署）

```text
未闭合项（ID + 缺口）:
业务影响:
为什么必须现在做 / 推迟的代价:
补偿控制:
接受范围: 仅本次变更（不得写成「今后同类变更」）
有效期 / 复审点:
接受人（姓名 + 账号）:
接受时间:
留痕位置: 工单 / PR 评论 / 运行记录 / 本卡 ID
撤销条件:
```

规则：

- 执行者 / agent 不得代填；空白 = 未接受。
- 只覆盖业务命题未闭合；不能修补授权包缺项、回滚路径缺失、证据缺失、
  判定人不独立。
- 接受后卡状态是「已授权（带残余风险）」，不是「已验收」；业务命题
  仍未闭合，下一次变更要重新接受。
- 接受范围不得扩展到同类变更；不得用「负责人已知悉」代替具体缺口。

## 12. 卡状态与失效

```text
草稿 → 待 owner 批准 → 已授权 → 执行中 → 待验收 → 已验收
                                             ↘ 已回滚
        ↘ 已拒绝
任意状态 → 已失效
```

只有 owner 能把「待 owner 批准」改为「已授权」，或签署 §11。

以下任一出现，卡立即「已失效」：

- 变更范围、环境、时间窗变化；
- 证据不是所列采集人采集；
- 假设被证伪；
- 回滚路径失效（快照丢失、`previous_revision` 不可部署、权限恢复来源缺失）；
- 模型 / 工具 / 数据源变更，触发授权复审；
- 登记表或 ADR 版本变化，导致字段 / 状态口径不再适用。

## 13. 短表（低风险变更）

用于可逆、无外部影响、无审计要求的改动。至少填：

```text
卡 ID / 日期:
变更内容:
影响面（一句话）:
回滚动作:
执行者 / 判定人:
一条可验证的完成命题:
```

短表不得用于 C-1 至 C-6 或任何后果性变更；若不确定，按全卡填。

## 15. 已知局限

- 首次试填样本见 `runs/2026-11-13-CHANGE-1.md`；它是本仓库的文档变更，
  不是 JOB-0 场景的重跑，不能当作产品发布样本。
- 本卡是登记面，不是证据；填得完整不等于变更安全。
- 业务命题的层级是判断，不是机械规则；owner 可能把控制动作当成业务结果。
- 没有真实案例时，本卡只能证明「字段齐全」，不能证明「组织会执行」。
- 组织必须先登记证据能力与输入集合；否则整张卡只能到假设可达。
- 低风险变更用全卡会制造仪式感；不确定时先问「错了能不能轻易回滚」。
- v1 只覆盖单次变更；跨迭代的同类风险需要另开卡或在 §11 的复审点里处理。
